# Bug hunt — 2026-09-02

An 18-subsystem sweep, every finding put to three independent verifiers instructed to refute it
and to default to refuted when unsure. 261 agents; 81 findings raised, 6 refuted, 71 survived.

**Treat the survival rate with suspicion.** 88% is too high for an adversarial pass, and it means
the bar was too low, not that the code is 88% broken. Everything below is a *lead*, not a verdict.
The ones marked FIXED were re-verified by hand against the real code before anything was changed;
several of those were also reproduced in the running app.

Ordered by claimed severity, which is the finders' own and is not always right — one verifier
argued the top finding down from data-loss to high, with reasons worth reading.


## data-loss (3)

### Rule "Move to mailbox" / "Move to Trash" never reaches the server; the queued op is discarded **[FIXED]**

`src-tauri/src/rules/engine.rs:311` · rules-junk · certain · 0/3 verifiers refuted

**What is wrong:** `apply()` performs rule moves with `crate::db::write::move_to` (engine.rs:311 for MoveTo, :368 for Delete) and nothing else. Every other caller of `write::move_to` — `ipc/mail.rs:520-538`, `:597-621` — first builds a real server op with `ops::locate` + `ops::enqueue(&Op::Move{..})`. The rules path skips that. The only queue row left behind is the legacy one `write.rs:291` writes: `enqueue(tx, "move", ids, Some(("mailboxId", mailbox_id)))`, whose payload is `{"ids":[..],"mailboxId":N}`. `ops::Op` is `#[serde(tag = "kind", ...)]` (ops.rs:39), so that JSON has no `kind` field and `ops::queued` (ops.rs:255) fails to deserialise it, logs "pending_op payload could not be read; dropping it", and DELETEs the row (ops.rs:258-259). The `kind` *column* says "move", which is all the one test (db/tests_queries.rs:374-399) checks — it never asserts the payload parses.

**Failure:** User creates a rule "if From contains newsletter → Move to Archive". Mail arrives; the message moves to Archive in Halcyon and the server is never told, so it is still in INBOX on their phone. On a later sync of Archive, local count exceeds server EXISTS, so `reconcile_expunged` runs `persist::remove_missing` (persist.rs:411-448), the message's INBOX UID is not in Archive's UID set, and the local row is DELETEd. INBOX's `uid_next` has already advanced past that UID and the backfill is finished, so it is never re-fetched. The message is gone from the client entirely while still sitting unread on the server.

### Autosave records a draft as saved before the write succeeds, so a failed save is never retried

`src/features/compose/useAutosave.ts:69` · compose-ui · likely · 0/3 verifiers refuted

**What is wrong:** lastSaved.current is assigned at line 69, before composeSaveDraft is even called. ## high (34)

### An empty newest page permanently marks the Inbox backfill "complete"

`src-tauri/src/sync/engine.rs:713` · sync-engine · likely · 0/3 verifiers refuted

**What is wrong:** The backfill cursor is seeded from `written.lowest_uid` (engine.rs:711-714), the lowest UID in the first-page FETCH. `persist::write_batch` returns `lowest_uid = 0` when the batch came back empty (persist.rs:146-148). With `backfilled_to == None` the cursor becomes 0; with a stored checkpoint it becomes `uid.min(0.max(1))` = 1. Either way `fetch::backfill_window` immediately returns `None` (fetch.rs:421 — and the tests at fetch.rs:577-578 assert exactly that for cursors 0 and 1), the `while` loop body never runs, and execution falls to `checkpoint(db, mailbox_id, 1)` at engine.rs:779, which records the backfill as finished. `record_backfill_progress` only ever moves the marker downwards (persist.rs:392), so the state is unrecoverable.

**Failure:** A Gmail Inbox of the shape the module's own comment describes — 214 live messages with UIDNEXT at 106,287 — where none of the newest 500 UID slots still holds a message (all archived). `newest_range` asks for 105787:106286, the FETCH returns nothing, lowest_uid is 0, the backfill loop never executes, and backfill_uid is written as 1. The user's Inbox shows zero messages; every later sync takes the "backfill already complete" early return at engine.rs:700 (or the incremental "unchanged since the last sync" return at engine.rs:944), so the 214 messages never download. Only mail that arrives afterwards ever appears. The resume case is the same bug with an interrupted backfill: cursor collapses to 1 and the remaining tens of thousands of messages are abandoned.

### Without CONDSTORE, rules, junk filing, arrival alerts and expunges never run

`src-tauri/src/sync/engine.rs:575` · sync-engine · certain · 0/3 verifiers refuted

**What is wrong:** The `if let (true, false, Some(..), Some(..), Some(..))` gate requires `caps.has_modseq()` (condstore || qresync, session.rs:246), so `incremental()` is unreachable on a server that advertises neither — such a server also never stores a `highest_modseq`, so the other conditions can never become true either. `incremental()` is the ONLY caller of `reconcile_expunged` (engine.rs:957, 1041), the only caller of `rules::engine::run_on_arrival` (engine.rs:993), the only caller of `upkeep::score_new_mail` (engine.rs:1004) and the only place `mail:arrived` is emitted (engine.rs:1016; grep confirms no other emitter). The comment at engine.rs:951-956 claims the expunge check is kept precisely so non-CONDSTORE accounts are covered, but that code cannot execute for them.

**Failure:** An account on any IMAP server that does not advertise CONDSTORE/QRESYNC (plenty of Dovecot builds, Courier, several consumer hosts). Every sync takes the full path: mail arrives and is stored, but no rule the user wrote ever fires, the junk classifier never files anything, no new-mail notification is raised, and mail deleted or archived from the phone is never removed locally — the exact symptom `reconcile_expunged`'s doc comment says it exists to fix, including the "opens to a blank body forever" follow-on.

### Import of more than 5,000 messages hangs forever in a non-paging rethread loop

`src-tauri/src/transfer/import.rs:239` · sync-persist · certain · 0/3 verifiers refuted

**What is wrong:** `import::finish` loops `while remaining > 0 { let done = rethread(tx, account_id, 5_000); if done == 0 { break } ... }`, treating `rethread`'s `limit` as a page size. It is not. `persist::rethread` (src-tauri/src/sync/persist.rs:170-176) always selects the *same* rows — `SELECT ... FROM message WHERE account_id = ?1 ORDER BY date_received DESC LIMIT ?2` — with no offset and no `thread_id IS NULL` predicate, and returns `assignments.len()`, which is `min(total_messages, 5000)`. Once the account holds more than 5,000 messages, every iteration re-threads the identical newest 5,000, `done` is always 5000 so the `done == 0` break never fires, and `unthreaded_count` (persist.rs:325-329, counts `thread_id IS NULL` across the whole account) never reaches 0. The loop never terminates. It runs inside `db.write(...)` (src-tauri/src/ipc/transfer.rs:244 and :465), i.e. on the single writer actor holding an open transaction.

**Failure:** User imports a Thunderbird profile or an mbox archive containing 6,000 messages. All 6,000 rows are written, then `finish` spins: threads the newest 5,000, sees 1,000 still unthreaded, threads the same 5,000 again, forever. The writer actor never returns, so every other DB write in the app (mark read, flag, move, send) queues behind it and the whole client freezes with no error. The transaction is never committed, so when the user force-quits, the entire import is rolled back and nothing was imported. A second, small import hits the same hang: importing 100 messages of *old* mail into a local account that already holds 5,000+ messages leaves those 100 outside the newest-5,000 window, so `remaining` stays at 100 while `done` stays at 5000.

### 5,000-message rethread window permanently splits conversations and re-keys threads

`src-tauri/src/sync/persist.rs:175` · sync-persist · certain · 0/3 verifiers refuted

**What is wrong:** `rethread` selects only the newest `limit` messages (`ORDER BY date_received DESC LIMIT ?2`) but then unconditionally rewrites `thread_id` for every message it did select (persist.rs:242-247). The engine calls it per batch with `RETHREAD_WINDOW = 5_000` (src-tauri/src/sync/engine.rs:639, :741, :977). Links to messages outside the window are invisible: `by_message_id` in `thread_messages` is built only from the selected slice (threading.rs:177-182), so a reference to an out-of-window parent falls into `by_missing_reference` and the message is keyed to itself. `Assignment.thread_key` is documented as "the smallest message id in the thread" and stable "as long as the membership does not [change]" (threading.rs:41-44), but the window silently changes the membership `rethread` can see, so the key can move *upwards*. Nothing repairs it: the `FULL_RETHREAD` pass at engine.rs:449 is gated on `unthreaded_count > 0`, and after the first full pass every message has a non-NULL `thread_id`, so it never runs again.

**Failure:** An account holds 20,000 messages, all correctly threaded by the one full pass at the end of the initial sync. A reply arrives to a conversation whose other messages are all older than the newest 5,000. `rethread` runs over the window, does not see the parent, and gives the reply `thread_id = <its own id>` and a fresh `thread` row. Opening it in the reader (`query::thread_get`, src-tauri/src/db/query.rs:326-336, `WHERE thread_id = ?1`) shows a conversation of exactly one message, and the list shows it separately from the conversation it belongs to. The same happens to any thread straddling the window edge: its in-window members are re-keyed to a new id while its out-of-window members keep the old one, splitting an existing conversation in two. Both splits are permanent.

**What is wrong:** `Op::AppendDraft.replaces` is filled from `draft.remote_uid` (src-tauri/src/ipc/compose.rs:1058-1070), but nothing in the repo ever writes that column — `grep -rn remote_uid` finds only the schema (migrations/0006_drafts.sql:16) and that one SELECT. `apply()` never records the UID the APPEND produced either. ### text_from_html panics on non-ASCII inside a comment, <script> or <style>

`src-tauri/src/sync/bodies.rs:247` · bodies-render · certain · 0/3 verifiers refuted

**What is wrong:** In skip mode the loop advances `index += 1` one BYTE at a time (line 252) but re-slices `lowered[index..]` on every iteration (line 247). `to_ascii_lowercase()` preserves the UTF-8 byte layout, so the first multi-byte character inside a skipped region puts `index` on a continuation byte and the `str` slice panics with 'byte index N is not a char boundary'. The main loop is safe because it only slices at an ASCII `<`/`>`; the skip branch is the one unguarded slice. `[profile.release] panic = "abort"` (Cargo.toml:156) and there is no catch_unwind on the call path (sync/engine.rs:1191, transfer/import.rs:223), so this aborts the process rather than unwinding one task.

**Failure:** Sync fetches the body of an HTML-only message (no text/plain part, so parse() calls text_from_html at bodies.rs:133) whose markup contains a non-ASCII character inside a comment or a style/script block — e.g. `<!--[if mso]><td>Don't miss out</td><![endif]-->` with a curly apostrophe, or `<!-- Save 20% — today -->`. I compiled the function verbatim and ran it: all four such inputs panicked ('start byte index 21 is not a char boundary; it is inside \u{2019}'), while the all-ASCII control returned normally. Ordinary marketing mail does this constantly, so the app dies on a body-fetch batch and, because the body is never persisted, dies again on every retry — a crash loop triggered by a message someone sent you. Existing tests miss it: outlook_conditional_comments_do_not_reach_the_preview uses only ASCII inside comments, and multibyte_characters_survive_the_html_stripper puts the multibyte text outside any skipped region.

### Redirect's Resent-* headers are terminated with bare LF, not CRLF

`src-tauri/src/mail/outgoing.rs:583` · outgoing-mime · certain · 0/3 verifiers refuted

**What is wrong:** The `Resent-From/To/Cc/Date/Message-ID` block is built with multi-line string literals (`"Resent-From: {}\n"` at 583-584, and the same shape at 590, 597, 604, 609). The file is stored with LF endings on disk (verified with od), so each header line ends in a bare LF. That block is prepended verbatim to the cached original, whose lines are CRLF (bodies.rs:110 writes the IMAP bytes unmodified), and the result is written to the outbox and handed to `send_raw` (sync/smtp.rs:203). lettre's SMTP `ClientCodec::encode` only dot-stuffs — its own unit test shows `"test\n"` transmitted unchanged — so the bare LFs go on the wire inside DATA. RFC 5321 §2.3.8 requires CRLF; the module doc at outgoing.rs:19 even names bare line feeds as something the target renderer rejects. No test asserts the line endings.

**Failure:** User redirects a message. Submission servers that enforce bare-newline rejection (Postfix >=3.9 smtpd_forbid_bare_newline, and the major providers) refuse the DATA, so the redirect fails in the outbox and retries forever. On a server that accepts it, a strict CRLF parser downstream folds the whole Resent block plus the original `From:` into one header value, so the message arrives with no visible From, Subject or Date.
